# UI Vision and Design: The AI Collaboration Control Room

## 1. Vision

The primary vision for this UI is to create an interactive **"Control Room"** for the multi-agent system. It aims to move beyond a simple command-line interface to a rich, transparent, and intuitive web application where a user can not only interact with the primary agent but also observe the entire "behind the scenes" orchestration in real-time.

This tool is designed for developers, testers, and stakeholders to gain a clear and immediate understanding of the system's behavior, debug issues, and verify the logic of the agent collaboration.

## 2. Core Design Goals

*   **Transparency:** The UI must demystify the "black box" of the agent system. It should explicitly visualize every significant event, decision, and data transfer between agents.
*   **Interactivity:** The user should be the primary driver of the workflow. The interface should provide a seamless and responsive way to chat with Agent1 and initiate tasks.
*   **Clarity & Intuitiveness:** The potentially complex flow of information must be presented in a simple, scannable, and aesthetically pleasing manner. The user should be able to understand the state of the system at a glance.

## 3. Key Features & Layout

To achieve these goals, the UI is designed with a two-panel layout:

### 3.1. Left Panel: Chat Interface

This is the user's command center.

*   **Function:** A standard, familiar chat interface for sending messages to and receiving text responses from Agent1.
*   **Components:**
    *   A message display area showing the conversation history.
    *   A text input field for composing new messages.
    *   A "Send" button to submit the request to the backend orchestrator.

### 3.2. Right Panel: Orchestrator Log

This panel is the "one-way mirror" into the system's brain.

*   **Function:** Displays a real-time, chronological log of all events happening within the `TopLevelOrchestrator`.
*   **Card-Based Design:** Each event is rendered as a distinct "log card" for maximum readability. Proposed card types include:
    *   **Decision Card:** Shows Agent1's intent (e.g., "Decided to call a function," "Decided to request function creation").
    *   **Function Call Card:** Displays the specific function and arguments the agent wants to execute. The JSON payload will be pretty-printed.
    *   **Execution Result Card:** Shows the output returned after a function is executed by the worker.
    *   **Agent Handoff Card:** Visualizes the data being passed from one agent to another (e.g., the "Task Brief" sent from Agent1 to Agent2).
    *   **Status Card:** Indicates changes in the task's lifecycle state (e.g., `CLARIFYING` -> `BUILDING`).
*   **Visual Cues:** Each card type will have a unique icon and color-coded border to make the log flow easy to follow.

## 4. Proposed Technical Architecture

*   **Frontend:** A **React.js** single-page application located in the `/ui` directory.
*   **Backend:** A **Python (FastAPI)** server (`main.py`) that acts as a lightweight bridge between the frontend and the core Python orchestrator logic.
*   **Communication:**
    1.  The React frontend is loaded in the browser.
    2.  It makes a `GET` request to a `/api/state` endpoint on the FastAPI server to fetch the current chat and log history.
    3.  When the user sends a new message, the frontend makes a `POST` request to a `/api/chat` endpoint.
    4.  The FastAPI server receives this request, passes it to the `TopLevelOrchestrator`, waits for it to process, and then stores the updated state.
    5.  The frontend automatically refreshes its state, showing the new user message and any subsequent events generated by the agents.

This architecture allows for a clean separation between the core agent logic and the presentation layer, and it enables near real-time visualization of the system's activity.
